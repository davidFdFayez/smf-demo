Why Clean Architecture

  • Domain has zero external dependencies — pure entities & invariants.
  • Application orchestrates: commands, validators, handlers.
  • Infrastructure is swappable: EF Core today, anything tomorrow.
  • API is a thin host that maps HTTP/JSON to commands.

Why CQRS + MediatR

  • Each business action is a single explicit Command.
  • Pipeline behaviors give us validation, logging, retries for free.
  • Read models can evolve independently from writes.
  • Testable end-to-end without spinning up the web host.

01

Membership Lifecycle

A single command-style endpoint, defended in three layers.

Smart, generated SMF ID

Format #SMF{YYYY}-{00001}. Allocated atomically with optimistic concurrency, so two sign-ups at the same instant never collide and never skip a number.

Defense in depth

  • UI hides irrelevant fields (Zod live validation).
  • Server re-validates with FluentValidation.
  • Domain entity enforces invariants on Member.Register().

Minor athlete protection

If Role = Athlete and age < 18, Guardian Consent is required — checked in UI, schema, server validator, and entity.

Medical clearance & approvals

Admin records clearance, approves or rejects. The state machine is on the entity itself, not scattered across handlers.

02

Payments — Reliability First

Webhooks are unreliable by nature. We design for exactly-once business effects.

Signed webhooks

Every payment provider callback is verified with HMAC against a shared secret. Forgeries are rejected at the door.

Idempotent state transitions

Payment.MarkSucceeded() is a no-op on duplicates. Replaying a webhook ten times produces the same single fee record.

Transactional outbox

PaymentSuccessfulEvent is staged in the same SQL transaction that flips the payment row. A background poller dispatches it through MediatR with bounded retries.

Atomicity across processes

Crash mid-handler? The outbox row stays pending and the next poll picks it up. No event is ever lost.

One QR code. Works without internet. Cannot be forged. Revocation-aware.

03

Digital ID at the Gate

How it works

  1. Issue — server signs an HMAC-SHA256 token: base64url(payload).base64url(sig).
  2. Cache — Flutter stores it in Hive; QR renders on first paint, no spinner.
  3. Scan — gate device scans, calls /admissions/verify.
  4. Verify — server re-checks signature and live RegistrationStatus.
  5. Refresh — app silently re-issues at the offline→online edge.
HMAC-SHA256 iat / exp Bilingual EN/AR + RTL

#SMF2026-00042 — Approved

Token valid · 24h · revocation-aware

Gate Decisions — Every Outcome Is Explicit

All denials are HTTP 200 on purpose, so dashboards distinguish "scanner offline" from "token rejected".

OutcomeHTTPWhat it means at the door
Admitted200Signature valid, in window, status Approved or Active.
TokenMalformed200Cannot parse payload.sig. Likely a non-SMF QR.
SignatureMismatch200Forgery, replay across environments, or rotated signing key.
NotYetValid / Expired200Outside iat/exp window (clock skew honored).
MemberUnknown200Token references a member id that no longer exists.
MemberNotInGoodStanding200Live status is Pending / Suspended — denied even with a valid token.

Live Demo Flow

Five minutes, end-to-end. Works on the demo URLs at the back of this deck.

1 · Register

On the public site, register an athlete. Watch #SMF2026-XXXXX appear instantly. Try a minor without guardian consent — see the inline server error.

2 · Approve

In the admin, approve the new member. Status flips Pending → Approved. Federation now has a real, addressable member.

3 · Scoreboard live

Open the public scoreboard for a match. In admin, drive Scoring / Head Referee / Timekeeper consoles — the public page updates in real time.

4 · Bracket generate

In Brackets, click Generate from registrations. Open the public tournament page — the bracket renders with connectors as bouts complete.

5 · Digital ID

Issue a digital ID for the athlete. Scan the QR at the gate (or call /admissions/verify) — admitted, expired, or denied with a clear outcome.

6 · Resilience

Replay a payment webhook ten times — exactly one fee row. Kill the API mid-flow — outbox replays the event on restart. Nothing lost.
